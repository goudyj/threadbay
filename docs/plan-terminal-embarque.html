1. Vision & objectif

Aujourd'hui Orchestrate crée des espaces (clone + branche depuis une base) et les ouvre dans un IDE. L'étape suivante : en faire une salle de contrôle d'agents. Depuis un espace, on lance un agent (Claude Code, Codex, ou une commande custom) qui tourne dans un vrai terminal, embarqué dans la fenêtre, avec suivi du cycle de vie (démarré / en cours / terminé), possibilité de relancer/arrêter, et une vue d'ensemble des agents actifs en parallèle. C'est là que le nom « orchestrate » prend tout son sens.

Pourquoi embarqué plutôt que Ghostty externe Un terminal externe (Ghostty) est du « lance et oublie » : l'app perd la main sur le process, ne connaît pas son état et ne voit pas sa sortie. En embarquant le terminal, on possède le process : statut par espace, badges, relance, arrêt propre, une seule fenêtre pour tout piloter. Aucune dépendance à Ghostty.

2. Ce qu'on réutilise

  • Les espaces & le tracking — SpaceStore / spaces.yaml. Un agent se lance dans space.destination.
  • La résolution du PATH — on relance via un login shell (zsh -lc) pour retrouver claude (dans cmux.app) et codex (homebrew), exactement comme dans un terminal.
  • La fenêtre AppKit — la NSWindow pilotée par l'AppDelegate qu'on vient de mettre en place accueillera la zone terminal.
  • Le modèle agent_commands — déjà présent dans settings.yaml avec placeholders ({space_path}, {task_value}, {base_branch}…). Piste pour définir « quels agents proposer » (voir §7).

4. SwiftTerm & le PTY

SwiftTerm (Miguel de Icaza, MIT, dispo en SPM) est un émulateur de terminal Swift mûr. Sur macOS il fournit LocalProcessTerminalView (une NSView) qui : crée un pseudo-terminal (forkpty), lance un sous-process, gère le rendu (couleurs, écran alternatif, scrollback), la souris, le copier-coller et le redimensionnement (TIOCSWINSZ).

Points d'intégration clés

  • Ajouter la dépendance SPM SwiftTerm au target Orchestrate.
  • Envelopper LocalProcessTerminalView dans un NSViewRepresentable pour l'utiliser en SwiftUI.
  • Lancer : startProcess(executable: "/bin/zsh", args: ["-lc", "exec <agent>"], environment: …) avec le répertoire courant positionné sur l'espace.
  • Le délégué LocalProcessTerminalViewDelegate notifie : processTerminated(exitCode), sizeChanged, setTerminalTitle, hostCurrentDirectoryUpdate → on s'en sert pour l'état de la session.
// Esquisse (signatures indicatives, à confirmer au spike)
final class AgentSession: Identifiable, ObservableObject {
    let id = UUID()
    let space: TrackedSpace
    let agent: AgentDefinition
    let terminalView: LocalProcessTerminalView
    @Published var state: State   // .starting / .running / .exited(Int32)

    func start() {
        let env = Terminal.getEnvironmentVariables(termName: "xterm-256color")
        terminalView.startProcess(
            executable: "/bin/zsh",
            args: ["-lc", "cd \(space.destination.shellQuoted); exec \(agent.command)"],
            environment: env)
    }
    func stop()    { /* SIGINT puis SIGTERM sur le pid du PTY */ }
    func restart() { /* stop + nouveau process */ }
}
À dérisquer en premier Claude Code et Codex sont des TUI plein écran (écran alternatif, souris, redraw). SwiftTerm supporte ça, mais c'est le point à valider par un prototype avant tout le reste (phase 0). Si le rendu et l'interaction sont bons, le reste est de la plomberie.

6. Interface proposée

Trois dispositions envisageables pour la zone terminal dans la fenêtre principale :

DispositionIdéePour / contre
Pane bas Liste des espaces en haut, terminal de l'agent sélectionné en bas (comme un IDE). Familier · garde le contexte espaces visible · terminal parfois à l'étroit.
Onglets d'agents Une barre d'onglets (un par agent actif), le terminal occupe la fenêtre. Beaucoup de place au terminal · vue « multi-agents » claire · on quitte la vue liste.
Sidebar + terminal Sidebar = espaces (badge « agent actif »), zone principale = terminal de l'espace sélectionné. Cohérent avec l'UI actuelle (NavigationSplitView) · un agent visible à la fois.
Décidé (n°1 & n°2) Sidebar + terminal (prolonge le NavigationSplitView existant). Comme un espace peut héberger plusieurs agents (décision n°2), on ajoute au-dessus du terminal un sélecteur des sessions de l'espace (petite barre d'onglets), plus une barre d'actions (relancer / arrêter / effacer). Le badge dans la sidebar indique le nombre d'agents actifs par espace (et signale « a besoin de toi » le cas échéant).

10. Risques & inconnues

Risque principal Rendu des TUI plein écran. Claude Code / Codex utilisent l'écran alternatif, la souris, des redraws fréquents. À valider dès la phase 0. Mitigation : SwiftTerm gère ces cas ; si un détail coince, on ajuste (mode souris, TERM).
Cycle de vie des process Bien tuer les enfants à la fermeture (pas d'orphelins), gérer un agent qui crashe/quitte, et le cas « espace supprimé pendant qu'un agent tourne dedans ».
Distribution future Aujourd'hui l'app est signée ad-hoc, non sandboxée → PTY + exec arbitraire OK. Si un jour on veut notariser avec App Sandbox, le spawn de process devient contraint (entitlements). À garder en tête, non bloquant maintenant.
Ressources N agents = N process + N vues terminal. Surveiller la conso avec plusieurs agents actifs ; envisager de suspendre le rendu des terminaux non visibles.

11. Notifications & détection de fin

Objectif : être prévenu quand Claude/Codex a fini son tour, a besoin de toi, ou quand la session s'est terminée. Comme cmux (lui-même basé sur Ghostty), on combine plusieurs canaux, du plus simple au plus sémantique. Puisqu'on possède l'émulateur et le lancement, on sait toujours quelle session émet le signal.

Canal 1 — Fin du process (gratuit)

SwiftTerm nous notifie via processTerminated(exitCode) quand la CLI de l'agent se termine = « session terminée ». Zéro config, mais sémantique pauvre (ne distingue pas « tour fini, session encore ouverte »).

Canal 2 — Séquences d'échappement terminal (OSC 9 / 777 / 99)

L'un des deux canaux de cmux. Beaucoup d'outils émettent des séquences « notification bureau » directement dans le flux terminal. Comme on possède SwiftTerm, on les intercepte à la source : on récupère titre+corps et la session émettrice, sans toucher à aucun fichier de config.

Note Peut nécessiter une petite extension de SwiftTerm pour exposer OSC 9/777/99 (il gère déjà d'autres OSC).

Canal 3 — Hooks des agents (le signal sémantique)

Le cœur de l'approche cmux, et la réponse à la question : oui, ce sont des hooks.

  • Claude Code — hook Stop (le tour principal est fini) et hook Notification (dont le champ message distingue permission_request = « a besoin de toi » de l'idle). Le hook reçoit un JSON sur stdin (session_id, cwd, transcript_path…).
  • Codex — clé notify appelée sur l'événement agent-turn-complete, avec un JSON en argument.

Injection non invasive (on ne touche pas à la config globale de l'utilisateur) :

  • Claude : écrire un .claude/settings.local.json dans l'espace (déjà un clone jetable) avec nos hooks.
  • Codex : passer -c 'notify=["orchestrate","notify"]' au lancement (override par process, pas de modif de ~/.codex/config.toml).

Comment l'app reçoit le signal

On maîtrise le lancement de l'agent : on injecte dans son environnement ORCHESTRATE_SESSION_ID (identité) et ORCHESTRATE_SOCK (adresse du socket). Le hook/notify appelle un petit notifieur (sous-commande orchestrate notify … ou script) qui transmet {session_id, type, title, body} :

Transport retenu — socket local (décision n°8) Un socket de domaine Unix que l'app ouvre au démarrage ; le notifieur s'y connecte et envoie le message en temps réel. C'est exactement le choix de cmux (/tmp/cmux.sock + CLI cmux notify). Le script teste l'existence du socket et devient un no-op si l'app n'est pas lancée. Fallback simple si besoin : un fichier déposé dans ~/.orchestrate/events/ et surveillé (FSEvents).

Note : on ne présuppose aucun binaire d'agent particulier — claude/codex sont résolus via un login shell, comme n'importe quel terminal.

L'app mappe session_id → AgentSession, met à jour le badge d'état de l'espace et poste une notification macOS (framework UserNotifications ; autorisation demandée une fois ; clic → focus l'app + sélectionne la session). Le bundle id (com.jlex.orchestrate.app) est déjà en place.

Leçon de cmux Un statut « hook-only » peut devenir muet si un hook manque (constaté côté Codex — issue #3749). D'où l'intérêt de plusieurs canaux : hooks (sémantique) + OSC + fin de process (filet de sécurité).
